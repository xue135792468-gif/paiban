# 08 验收准备（尚未施工）

05正在施工，06/07/08未施工；以下是统筹的验收设计，不是通过证据。原始票见issues/08-end-to-end-acceptance.md。

## 整链公开行为

- 后端以假钉钉和真实HTTP进入：唯一未绑定教师自动配对开号→Teacher提交COVER待批→另一教务管理员改人批准→新课表实际教师改变→申请人与最终接课老师收到正确类型记录→账号审计、调代成功审计、状态历史可查。
- 至少三位不同教师（原教师/申请人、期望代课人、最终代课人），以及独立的教务账号。不能仅用同一账号扮演所有角色而漏掉operator和teacher的差别。
- 断期望人保留、最终人不同；通知仅对应申请人和最终人，不发给期望人、班主任、教务或旧名单；审批结果含真实结果，接课内容有日期/节次/班/课。网络成功只证明fake或stub受理，不代表实机送达。
- Playwright用Teacher手机视口免登提交、Academic电脑视口待审批批准、Teacher刷新我的申请看到已生效。保留控制台错误收集，断稳定DOM/URL/接口结果，不以toast作为唯一证据；共享交互复用helpers.ts，所有跨spec种子名称唯一。

身份隔离前置：现有Fake默认EMP001/dd-001/张三与EMP002/dd-002/李四会被其他通讯录/免登spec使用，不能假设它们没有账号，更不能降级/改绑别的fixture来强行获得Teacher。08施工时评估最小Fake合成身份能力或等效隔离方案，保持默认两人目录及既有用例，不增加面向产品的测试控制端点。SDK可注入假authCode，但认证POST必须真的经过后端；不能route伪造JWT响应来声称整链。只对自己确切创建的账号/Teacher做收尾，不触碰他人的记录。

## 存量升级

复用RoleUpgradeDataPreservationTest的V59建旧库与业务种子思路，但新增覆盖**全部当前新迁移**的独立验收，不把旧V59→V60单票绿例冒充全特性升级。

- 旧admin及另一旧管理员均变super_admin，旧head_teacher变teacher，普通教师保留。退休角色不再可选，老师全校只读与教务权限减项按角色结果断言。
- V61/V62/05审批列会增加字段，不能对新旧SELECT *整行直接相等，也不能弱化为只比行数。先在V59捕获各表的旧列名及按ID排序的全部旧列值，升级后用同一旧列投影比较；另外单独断新列默认值/约束与索引等新增行为。
- 老账号的凭据校验字段、绑定、启停、旧业务主键与每个旧字段值保持；学期/作息/班级/教师/草稿/课节/基线/历史调代/约束/导入会话至少都有带数据对照。审批历史旧主体保留，新审批元数据未知时为空，不猜造旧审批信息。
- H2演练与真实PostgreSQL分开报告；没有Docker/真实PG就明确未验证，不能用H2证明生产数据库行为。

### 2026-11-13 统筹补核：旧列投影的明确例外

主控实读本集成源 V60–V63：当前最高 V63；06/07 的既定写集均无新迁移。08 仍须运行施工时 classpath 的全部迁移，不把本次版本快照写成永久上限。

- `app_user` 的旧列（包含 password_hash、绑定、enabled 等）逐值比较，新 login_type 单独断为 PASSWORD；不能因为角色升级而放宽旧账号列保全。
- `role`、`permission`、`user_role`、`role_permission` 是 V60 有意调整的授权数据，不能混进“所有旧表投影完全不变”的断言。对这些表分别断两个旧 admin 持有者转 super_admin、head_teacher 转 teacher、退休角色及预置权限变更，并明确旧自定义角色/其持有关系的既定保留语义。
- `audit_log` 全部旧列不改；V61 新增 category 对旧 APP_USER、users/IMPORT 事件分类 ACCOUNT，其余新增目标/快照字段为空，不凭空恢复未知历史。新增分类是独立断言，不能拿它豁免旧审计正文/主体保全。
- `substitution_request` 所有旧列和历史主体不改；V63 新审批列在旧行为空，新外键/索引另验。V62 的账号组合 CHECK、NOT NULL DEFAULT 与放宽密码列也独立验，不能只凭实体编译通过。

以上仅修正验收设计歧义，08 尚未施工或跑升级演练。
