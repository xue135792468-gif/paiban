## Comments

### 实现说明（后端，2026-10-26）

**迁移**
- 新增 `V26__constraint_entry.sql`：建表 `constraint_entry(id, semester_id, type, params_json, created_at)`，
  `id` 为 `GENERATED BY DEFAULT AS IDENTITY`（稳定条目身份），索引 `(semester_id, type)`，
  外键 `semester`（`ON DELETE CASCADE`）。
- 数据迁移：把 `constraint_config.params_json` 复制成该类型的**一条** legacy 条目。
  复制条件是「非 NULL、去空白后非空、且不等于 `{}`」——`{}` 不含任何对象条件，
  不复制时快照层合成「无条目」，与升级前 `{}` 的判定完全一致（见下）。
- `constraint_config` 原样保留 `(semester_id, type)` 唯一行，继续承载 `enabled/hard/weight`，
  `params_json` 在保存时同步写第一条条目的参数（旧读者/裸 SQL 仍看到有意义的值）。
- 迁移语法只用 H2(PostgreSQL 模式) 与真实 PostgreSQL 都支持的 DDL；迁移测试在 H2 上按
  「迁移到 V25 → 写入旧形状 → 迁移到最新 → 读回条目」验证，不是只断言表存在。

**表结构 / 实体**
- `scheduling/domain/ConstraintEntry` + `ConstraintEntryRepository`
  （`findBySemesterId`、`findBySemesterIdAndTypeOrderByIdAsc`、`deleteBySemesterId`）。

**API 契约**
- `GET /api/constraints` 仍是数组（不破老前端），每项新增 `entries: [{id, params}]`；
  `params` 保留为第一条条目（旧访问路径不变）。
- `PUT /api/constraints` 的 config 新增可空 `entries: [{id?, params}]`：
  - 不传 `entries` → 按 legacy 单条处理，`params` 即那一条（`{}` 表示无条目）；
  - 传 `entries` → 以 `entries` 为准（新建学期时 `id` 可省略，稳定 id 由服务端生成）；
  - 条目的 `id` 当前只做身份回传，不用于定位既有行（整学期保存是整次替换，见下）。
- 保存是整次事务：先全量校验所有类型与条目，任一非法即 400，原 `constraint_config` 与
  `constraint_entry` 不变（校验全部发生在删除/写入之前，异常回滚）。
- 校验覆盖：条目对象必须是已存在教师；`dayOfWeek` 1–7；`(星期, 节次)` 必须存在于该学期作息
  （学期没有作息时明确报错，要求先配作息）；**完全相同的条目拒绝重复**；同一类型在一次请求里
  出现多次直接拒绝（启用/软硬/权重是类型级控制，结构上不允许两条不同控制）。错误信息格式
  `类型显示名(类型码) 第N条: ...`，legacy 单条路径保留原措辞。
- 权限/审计不变：仍走 `Permissions.CONSTRAINT_MANAGE` 与既有事务边界，未新增角色字符串。

**legacy 合成规则（`ConstraintSettings`）**
- `Rule(hard, weight, entries)`；`from(configs)` 等价 `from(configs, List.of(), mapper)`。
- 某类型有条目行 → 用条目行（按 id 升序）；没有条目行 → 用 `constraint_config.params_json`
  合成一条（仅当解析出非空 map）；`{}`/空 → 无条目。
- 旧访问器 `params/longParam/intParam/textParam/matchesCourse` 取第一条条目，因此
  22 个未扩展类型的行为（含「空 params = 全部对象」这类语义）与改动前逐字一致。
- 新增 `entries(type)` 供多条目评估使用。

**各评估入口改动点（性质）**
- `ConstraintChecker`（草稿校验/发布/调代软硬扫描共用）：`TEACHER_UNAVAILABLE` 由「读单组参数」改为
  「遍历 `entries(type)` 的并集」，命中任一即一次违反（同一节课不会因多条命中重复计）。
- `PaibanConstraintProvider`：同一并集语义，改为按教师聚合 (星期, 节次) 集合再过滤；
  只有条目非空时才注册该约束（原来判断 `teacherId != null`）。
- `SwapPlanner.placeable`：同一并集语义（计划生成的边剪枝）。
- `PlanVerifier`：不复制规则，继续走 `ConstraintChecker.checkHardFast`，因此自动一致；
  审批时按**当前**快照重新构建设置并重验，新增禁排会让旧方案整单拒绝（`snapshotHash` 只覆盖课表，
  所以新增回归测试走的是真实重验路径而不是快照相同即放行）。
- `SubstitutionCli`：快照 JSON 的 constraint 支持 `entries`（含可选 `id`，无 id 时按出现顺序编号），
  仍兼容只有 `params` 的旧快照。
- `SchedulingService` / `DraftValidator` / `PlanSnapshotFactory`：统一改为调用
  `ConstraintService.settings(semesterId)`——求解、草稿、发布、调代、CLI 都由这一处装配快照。

**模板**
- `constraint_template.configs_json` 结构扩展为同一 config 对象内可带 `entries`；
  保存模板时 `entries` 存在则不再重复写 `params`（省容量），读取时兼容无 `entries` 的旧模板。
- 套用模板走同一个 `save(...)`，条目完整恢复（跨学期班级引用重映射属于 05）；
  超过 `configs_json` 的 8000 字符上限时明确 400 报错，**不静默截断**（未改 DDL：8000 字符
  足够本票条目量，且 `ALTER COLUMN` 在 H2/PG 的语法不同）。

**计数口径**
- 两个数由**前端**从既有响应计算，后端不另出一套：类型数用 `GET /api/constraint-types`
  的目录（24 类），已启用类型数 = `GET /api/constraints` 中 `enabled` 的项数；
  条目数 = 各类型 `entries.length` 之和，开关型（`params` 声明为空的 6 类）不计入。
  后端只保证 `entries` 与目录 `params` 两个事实字段，避免两处各算一套。

**测试**
- `ConstraintEntriesCheckerTest`（纯 checker）：两教师互不影响、同一教师两个时段都拒绝、
  他人条目不影响本课、legacy 单组参数与显式一条条目判定逐字相同、`COURSE_NOT_IN_EVENING`
  与 `TEACHER_MAX_PER_DAY` 两种未扩展类型行为不变。
- `EngineConstraintTest` 新增两条：多条条目全部计硬分、他人条目不扣分。
- `ConstraintEntriesIntegrationTest`（公开 REST）：两教师/同教师两条落库并可重读、重复 400 且配置不变、
  非法教师/星期/超作息 400 且配置不变、legacy 请求合成一条、其余类型 params 语义不变、
  模板往返（3 条完整恢复）、旧格式模板仍可套用、草稿校验与发布同时拒绝两个禁排时段。
- `ConstraintEntryMigrationTest`：V25→种子→V26 后旧 params 成为一条条目，`{}` 不产生条目。
- `SubstitutionCliTest`：快照里两条禁排让 plan 无解、verify 对同一事实给出 FAIL。
- `SwapApprovalReverificationIntegrationTest`：生成方案后新增禁排 → 审批 409、无任何替换记录、
  申请仍为 `PENDING_APPROVAL`。

**偏离设计与遗留风险**
- 保存时「同类型多条配置」用直接拒绝代替「控制不一致才拒绝」：请求结构上每条 config 自带
  控制，两条必然可写出一致或冲突两种状态，直接拒绝不会丢任何合法输入，且避免「按顺序覆盖」。
- 条目身份：本票一次提交替换整学期条目，`id` 只做回传与稳定表达；不做「按 id 增量更新/删除」
  的局部合并。前端编辑后整表提交即可；若将来要保留审计粒度，需要在条目加版本字段。
- 「全部对象」语义：`{}` 不落条目行（与 legacy 等价）。将来扩展 SPORT/SAME_COURSE 等多目标类型
  到 `entries` 前，必须先定义「空条目 = 全部对象」是否允许，否则会出现「显式空列表 vs 未配置」
  无法区分。当前仅 `TEACHER_UNAVAILABLE` 走多条判定，其余类型仍走单值访问器。
- 节次范围校验只作用于 `TEACHER_UNAVAILABLE`（其余 23 类保持原 schema 校验），
  避免本票改变它们「可保存但可能无意义」的既有行为。
- 模板容量仍是 8000 字符上限（明确报错）；若后续要存上百条条目，需要一次专门的加宽迁移。

**计数口径（单一定义处）**
- `draftRules.draftEntryCount(row)` 给出单类条目数，`draftRules.countsOf(rows)` 汇总三个计数；顶部汇总带与左侧组头都调用同一函数，不在别处再算一套。
- 开关型（目录 `params` 为空）恒为 0；多条目类型只计「会落库」的卡片（空卡片不计）；单参数类型有值即 1 条。
- 顶部 `/24 类` 的分母取**全部目录类型**，初中模式隐藏的 `TEACHER_MEETING_BLOCKED` 仍计入，也不从提交里删除。
- 计数读的就是 payload 将要提交的数据：不会再出现「卡上 12 条、服务端一条没有」。

**payload 形状**（`buildSavePayload`）
```json
{ "configs": [
  { "type": "TEACHER_UNAVAILABLE", "entries": [{ "id": 12, "params": { "teacherId": 3, "dayOfWeek": 4, "periodNo": 5 } }],
    "weight": 100, "hard": true, "enabled": true },
  { "type": "COURSE_NOT_IN_EVENING", "params": { "courseId": 9 }, "weight": 60, "hard": false, "enabled": true }
] }
```
- 只有 `TEACHER_UNAVAILABLE` 发 `entries`（不发 `params`），`id` 原样回传；空卡片不提交。
- 其余类型仍发 legacy `params`。**关闭的类型保留其参数**（开关只决定是否评估）；关闭且从未配置的行整条不发——
  后端对「必填参数为空」的配置一律 400，不发才是「没有配置」，也避免把目录默认值写成条目。
- 初中模式把软硬折成权重 100/50；请求始终包含隐藏类型（有值即发），不抹掉高中配置。

**Playwright**（`e2e/constraints-entries.spec.ts`，4 条串行用例，合成教师 张伟/李娜）
1. `添加两位教师各一条禁排，保存后刷新仍在` — 断言两条卡片摘要、顶部/左侧计数为 2、接口里两条条目带 id。
2. `删除其中一条后保存，刷新只剩一条` — 删除二次确认，刷新后只剩李娜那条，计数为 1。
3. `顶部「具体条目」与左侧「条目数」始终一致，开关型不计数` — 顶部=左侧求和、`/24 类`、开关型标「开关」。
4. `重复条目保存被拒：错误落在第 2 条，输入原样保留` — 前端重复提示 + 服务端 400 后错误落到第 2 张卡片。

**与原型 B 的差异 / 取舍**
- 原型「生效条目」把关闭类型算 0；本实现按用户确认的口径叫「具体条目」，计已配置（会落库）的条目，关闭但已配置的仍计 1 条。
- 条目在类型关闭时仍可编辑（原型如此，规格「关闭＝不评估、不删除」）；旧页面关闭时会清空参数，本页改为保留。
  配套把必填校验从「只看启用类型」放宽到「只看会提交的行」：空白卡片不提示，填了一半照样提示。
- 阈值「全局＋对象例外」卡片属于 04 票，本票其余类型仍是原单参数表单。
