# 排课系统九期规格：发布后调代课（调课置换环 + 代课）

Status: ready-for-agent

票据：`issues/01-snapshot-constraint-seam.md` … `08-e2e-and-docs.md`（依赖关系见各票 Blocked by）。

---

## Problem Statement

课表发布后，教师临时调整上课时间的真实流程远比系统现在能表达的复杂：

- 教师 A 的数学在周三第 3 节，他想换到周三第 2 节；第 2 节原本是教师 B 的英语。B 必须让位，A 原来的第 3 节又不能空堂，于是要在**同一个行政班的课表内**形成一次课节置换：A 的课去第 2 节，B 的课去第 3 节。这就是两人调课。
- 如果 B 第 3 节在别的班有课，就得再拉一位教师 C 进来：A→第 2 节，B→第 4 节，C→第 3 节。三人、四人，依此类推。参与的教师越少越好。
- 如果教师 A 是请假、不再补这节课，则只需要一位**代课**教师来接替第 3 节，可以是外班、同科的老师。

当前系统只有后者的简化版：`SubstitutionService` 一次只处理一节课、一位代课教师；审批时只校验「代课教师该节有没有课」，不校验教室、场地类型、教师禁排、学科和任何软约束；`new_period_id` 甚至不检查本班目标节次是否已有课。`substitution` 一次只写一行，没有「方案」概念，无法表达 2–6 位教师的置换环。ADR-0002 预留的 `substitution_group_id` 也从未实现。

结果是：教师线下自己找人，教务手工核对冲突，通知靠口头，期末统计分不清「调课」和「代课」，课表上也无法追溯一次调整到底动了几个人。

## Solution

把发布后的调代课拆成两类，用同一套确定性引擎处理：

1. **调课（同班置换环）**：把一个课节从原时间移到目标时间，并在同一行政班的课表内用置换环把原节次补满。涉及 2–6 位教师；班级当天的课节数量和课程集合不变，只有节次顺序变。
2. **代课（单向补位）**：原教师不能上课，另一位教师（可跨班，通常同科）接替该课节。只涉及一位教师的变动，不要求回填原节次。

调课由系统生成候选方案，教务选择并整单批准；方案必须通过独立校验器才能生效。搜索是纯确定性算法：同日优先，跨天在可配置窗口内（默认 7 个自然日）按影响天数、是否同周、影响教师数、软约束扣分排序；支持三个排序预设。AI 完全不参与可行性与排序，将来最多用于把已算好的方案或无解原因解释成人话。

同时提供只读的离线 CLI（`plan` / `verify`），吃 JSON 课表快照，给运维做 what-if 和事后核查。

## User Stories

1. 作为任课教师，我想在「我的调代」里选择「调课」，填请假日期、我的课节和希望换到的时间，这样我不用线下挨个找同事。
2. 作为任课教师，我想在提交前看到哪些目标节次是可行的，避免提交一个根本无解的时间。
3. 作为任课教师，我想在无解时看到脚本生成的具体原因（例如「赵老师第 3 节有课、刘老师第 4 节有课、当天班额无法抵消」），这样我知道该找谁协调或改选时间。
4. 作为任课教师，我想在「代课」类型下只选课节、填原因，代课教师可以指定也可以留空，这样突发请假能快速提交。
5. 作为任课教师，我想在「我的申请」里看到调课方案涉及哪几位老师、各自挪了哪一节，而不是只看到一个状态。
6. 作为被卷入的教师 B，我想收到一条只关于我自己的通知（「你的英语从周三第 2 节调到第 3 节」），不需要我逐个确认，这样流程不会卡在多人确认上。
7. 作为被卷入的教师，我想在课表的「最新」视角看到自己那节课被标成「调」或「代」，并能看到原因和原教师。
8. 作为教务管理员，我想在「待审批」里看到最多三个候选方案，每个方案显示影响天数、影响教师数、软约束扣分和涉及课节，这样我能按学校偏好选一个。
9. 作为教务管理员，我想整单批准一个 2–6 人的调课方案，系统一次性生效，绝不会出现「张老师换了、赵老师没换」的半截状态。
10. 作为教务管理员，我想在批准时如果课表已经变化，系统能拒绝旧方案并提示重新生成，而不是把冲突写进已发布课表。
11. 作为教务管理员，我想在设置里选择排序预设：最小影响、最少教师、最稳课表，默认最小影响。
12. 作为教务管理员，我想配置跨天搜索窗口（默认 7 天，最大 30 天）和方案教师数上限（默认 6 人），以适配不同学校的管理尺度。
13. 作为教务管理员，我想在批准代课申请时沿用现有流程，但系统也要跑一遍硬约束校验。
14. 作为教务管理员，我想在「调代记录」里按类型（调课/代课）、班级、教师、日期筛选，并看到一次调课方案的全部移动。
15. 作为教务管理员，我想在教师统计里分别看到「被代课次数」「代课次数」和「参与调课次数」，避免把调课虚算成代课。
16. 作为教务管理员，我想在一笔调课方案批准后，系统给所有被卷入教师、该班班主任和教务发通知，通知范围沿用现有设置。
17. 作为班主任，我想看到本班调课/代课的完整记录和原因，以便向学生和家长解释。
18. 作为年级负责人，我想在现有通知范围开关打开时收到本年级的调课通知。
19. 作为系统管理员，我想在学期末导出调课/代课明细，区分类型，供课时统计和代课费核算。
20. 作为系统管理员，我想让所有方案和审批动作留审计痕迹（谁、何时、生成了什么、批准了哪个、校验结果）。
21. 作为运维/教务，我想用一个只读 CLI 输入课表 JSON 快照，输出候选方案或校验结果，不连数据库、不落库。
22. 作为运维，我想在事后用 `verify` 命令对比改动前/后的课表，直接看到违反的约束，而不是翻日志。
23. 作为开发者，我想让求解器和校验器彼此独立：求解器可以出错，但错误方案绝对不能生效。
24. 作为开发者，我想让调课搜索不依赖 AI、Spring 或数据库，能在毫秒级用内存快照完成，便于单元测试和 CLI 复用。
25. 作为开发者，我想复用现有 24 类约束的硬/软定义与权重，避免草稿期和发布后两套规则漂移。
26. 作为开发者，我想让调课搜索按「日期 + 节次」建图，支持跨天，而不是把一周当成一张固定模板。
27. 作为开发者，我想让校验器检查「只有方案内的课节发生了变化」，防止求解器或写入逻辑误改其他课节。
28. 作为开发者，我想让校验器独立重算软约束扣分，和求解器报告的值比对，发现不一致就报警。
29. 作为开发者，我想让方案携带生成时的课表快照哈希，批准时重算，保证并发安全。
30. 作为开发者，我想让 CLI 的输入输出有版本号（schemaVersion），后续扩展不破坏已有脚本。

## Implementation Decisions

### 领域语言

使用 `GLOSSARY.md` 的术语：**调代课**是统称，**调课**是同班置换环，**代课**是单向补位，**置换环**是被挪动课节构成的闭环，**影响教师数**去重计教师，**影响天数**按日期去重。`换课` 仅指发布前草稿期的两节课交换，不复用于发布后。

### 数据模型

- `substitution_request` 增加：
  - `type`：`SWAP` | `COVER`，默认 `COVER`（兼容存量）。
  - `target_period_id`：调课的目标节次；代课为空。
- 新表 `substitution_plan`：一次调课生成的候选方案。字段包括请求 ID、生成时的课表快照哈希、排序预设、状态（`PROPOSED` / `APPROVED` / `REJECTED` / `EXPIRED`）、影响天数、影响教师数、软约束扣分、创建时间、过期时间、批准时间。
- 新表 `substitution_plan_move`：方案内每条课节移动。字段包括方案 ID、课节 ID、原节次、目标节次、教师 ID、目标教室（可空）、顺序。
- `substitution` 增加：
  - `type`：`SWAP` | `COVER`，默认 `COVER`。
  - `plan_id`：可空，指向产生它的方案。
- 调课的每一行 `substitution` 表示「一节课被挪动」：`original_teacher_id` 与 `substitute_teacher_id` 相同（教师跟着课走），`new_period_id` / `new_day_of_week` / `new_period_no` 是目标节次。代课沿用现有语义（换教师，不换节次）。
- 迁移版本为 **V22**（V20 / V21 已被八期占用）；存量 `substitution` 与 `substitution_request` 回填 `type='COVER'`。

### 搜索算法

- 图节点为「日期 + 节次」，只取该行政班在这些日期已有课节的槽位；节点携带该课节的课程、教师、教室。
- 有向边 `u → v` 表示「u 上的课节可以搬到 v」，建图时做硬剪枝：
  - 该课节教师在 v 的日期/节次跨所有班级空闲（基线 + 该日期已生效调代）；
  - 教师不在禁排/教研/请假时段；
  - 该课节教室在 v 空闲，且满足场地类型与容量；
  - v 属于同一行政班、同一学期、在搜索窗口内。
- 请求固定起始边：A 的课节从原节次 `O` 到目标节次 `T`。问题转化为在图上找一条从 `T` 回到 `O` 的最短简单路径；路径长度 + 1 为环长（被挪动课节数）。
- 搜索按「允许的影响天数」分层：先只允许同一天（影响天数 = 1），无解再放开到 2 天、3 天……直到窗口天数。每一层内用 BFS 找最短路径；同层多个解再按排序预设排序。
- 硬上限：环长不超过配置的最大教师数（默认 6）；搜索节点预算 5 万、时间预算 200ms；超预算返回当前最优或「无解」。
- 环结构天然保证每个涉及的日期「有进有出」，因此班级每天节数与每周总量不变；校验器仍会独立复核。
- 软约束只在候选环上计算增量，使用现有 `ConstraintType` 的权重；硬约束参与建图剪枝，不参与打分。
- 排序预设：
  - `min-impact`（默认）：影响天数 → 是否同周 → 影响教师数 → 软约束扣分。
  - `min-teachers`：影响教师数 → 影响天数 → 是否同周 → 软约束扣分。
  - `stable-timetable`：软约束扣分 → 影响天数 → 是否同周 → 影响教师数。
- 每份请求最多保留 3 个候选方案，按当前预设排序。

### 约束校验

- 复用现有 24 类 `ConstraintType` 的硬/软标志与权重；不另建调代专用规则集。
- 求解器做快速增量剪枝；批准前由独立校验器对「基线 + 全部生效调代」的最终课表做一次完整硬约束校验。
- 校验器必须独立实现至少四条核心不变量（暴力扫描，不与求解器共用 helper）：同一教师同一时刻只出现一次、同一班级同一时刻只有一门课、同一教室同一时刻只被占用一次、班级每天节数不变。
- 校验器还要检查：只有方案内的课节发生变化；每节课的课程与教师保持不变（代课除外）；软约束扣分与求解器报告值一致。
- 校验失败：整单拒绝生效，写审计日志并告警；接口返回具体违规清单。

### 接口与流程

- 创建申请：扩展现有创建接口，接受 `type` 与 `targetPeriodId`；调课必须提供目标节次，代课不允许提供目标节次。
- 生成方案：教务对一笔待审批的调课请求触发生成，系统持久化最多 3 个候选方案并返回方案 ID、移动列表、影响天数、影响教师数、软约束扣分。
- 批准方案：按方案 ID 整单批准；先重算快照哈希并跑校验器，再在一个事务内写 `substitution` 行、更新请求状态为 `EFFECTIVE`、发通知。
- 方案过期：默认 30 分钟；过期或快照变化时批准返回冲突，提示重新生成。
- 代课沿用现有批准接口，但批准前同样跑校验器。
- 权限沿用现有 `substitution:submit` / `substitution:approve` / `substitution:view` / `substitution:view:class`。
- 通知范围沿用 `notification.scope`：所有被卷入教师 + 该班班主任 + 教务；年级组长按现有开关。
- 统计：`substitution.type` 区分；「被代课/代课次数」只统计 `COVER`；调课单独统计「参与调课次数」；课时量按净变化计算。

### 设置项

- `substitution.search-window-days`：默认 7，范围 1–30。
- `substitution.max-plan-teachers`：默认 6，范围 2–10。
- `substitution.ranking-preset`：`min-impact` | `min-teachers` | `stable-timetable`，默认 `min-impact`。

### 离线 CLI

- 只读，不连数据库，不写业务数据。
- `plan`：输入快照 JSON，输出候选方案 JSON 或表格；参数包括窗口天数、最大教师数、排序预设。
- `verify`：输入改动前/后的课表（或快照 + 方案），输出通过/违规清单。
- JSON 带 `schemaVersion`；退出码 0 有解、2 无解、1 错误。
- 与后端共用同一套纯 Java 求解器与校验器；CLI 只是薄入口。

### 前端

- 「我的调代」表单增加类型切换：调课（日期、我的课节、目标时间）与代课（日期、课节、期望代课教师、原因）。
- 「待审批」增加方案卡片：每个方案显示移动列表、影响天数、影响教师数、软约束扣分、当前排序标签；整单批准/驳回。
- 「调代记录」增加类型标签与方案展开。
- 课表「最新」视角区分「调」与「代」标记。
- 设置中心增加窗口天数、最大教师数、排序预设。

## Testing Decisions

### 测试缝

1. **纯求解器缝**：`SubstitutionPlanner` 接受内存中的课表快照、请求与选项，返回候选方案或无解诊断。不依赖 Spring、数据库、AI。绝大多数算法正确性在这里测。
2. **纯校验器缝**：`PlanVerifier` 接受改动前快照、方案移动、改动后快照，返回通过或违规清单。与求解器独立，单独测。
3. **HTTP 集成缝**：教师提交 → 教务生成方案 → 批准 → 课表叠加 → 统计/通知。用现有 `ApiIntegrationTest` + `ScheduleFixture` 风格。
4. **CLI 缝**：同一套纯模块的薄入口，用 JSON golden 文件与进程级 smoke test 覆盖。

### 测试原则

- 只测外部行为：求解器测「给定课表快照，产生哪些方案/无解原因」，不测内部 BFS 步骤；校验器测「给定变更，是否拒绝及违规码」，不测私有方法。
- 优先使用现有缝：`DraftValidatorTest` 已证明仓库 mock + 纯 JUnit 的写法可行；`SubstitutionIntegrationTest` 已证明 RestAssured + `ScheduleFixture.published` 的写法可行。
- 算法测试使用小的内存快照（1 个班、5 天、每天 8 节、10 位教师），覆盖 2 人环、3 人环、跨天环、周五一班跨到下周一、无解、窗口边界、教师数上限、排序预设。
- 属性测试：随机生成合法课表与请求 → 求解器产出的每个方案 → 校验器必须通过；再随机篡改方案中的一条移动 → 校验器必须拒绝。
- 校验器专项：注入教师冲突、班级冲突、教室冲突、每天节数变化、方案外课节被改、软分不一致，逐条确认违规码。
- 并发测试：生成方案后由另一请求占用目标节次，批准必须整单失败且不产生任何 `substitution` 行。
- 统计测试：一笔 3 人调课不增加任何人的「代课次数」，只增加「参与调课次数」；一笔代课正常增加。
- CLI 测试：`plan` 与 `verify` 各一组 golden 输入输出；无解时退出码为 2。

### 既有测试先例

- `DraftValidatorTest`：Mockito mock 仓库，无 Spring，测约束校验的边界。
- `SubstitutionIntegrationTest`：`@SpringBootTest` + RestAssured，覆盖提交、审批、通知、统计。
- `SwapIntegrationTest` / `SwapCandidateIntegrationTest`：发布前换课的集成测试，可作为调课方案的对照。

## Out of Scope

- 跨班联合置换（多个行政班一起参与的环）；调课限定在同一行政班内。
- 目标节次为空时的「只挪不补」；该操作保留为教务的低层换时间能力，不走调课申请。
- 跨学期、跨周（超出搜索窗口）的调课。
- 批量请假、连续多天调课、整周调课。
- 教室变更作为独立主操作；调课中教室跟着课走，若目标节次教室不可用则该方案不可行。
- AI 参与求解、候选生成或排序；现有 AI 代课推荐仅保留在代课审批里，且仍是「规则出候选、AI 只排序/解释」。
- 学生与家长通知。
- 调课费、代课费的自动结算；只提供可导出的统计口径。
- 自动批准；调课必须经过教务。
- 修改已发布的基线课表（继续遵守 ADR-0008）。

## Further Notes
