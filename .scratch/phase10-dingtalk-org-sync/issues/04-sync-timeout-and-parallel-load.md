# 04: 钉钉同步预演/确认超时假失败 + 通讯录并发加载

**What to build:** 线上点「同步预演」弹「预演失败」，但后端日志显示预演成功——前端 30 秒超时先断开了连接，后端要 54 秒才爬完 49 个部门。把前端这两个接口的超时提到 180 秒并在按钮上说明耗时；同时把 `DingTalkDirectoryLoader` 的串行爬取改成按层并发（默认 4 线程），把 54 秒压到 10 秒左右。**不改匹配逻辑、不动票 03 的 12 项。**

**Blocked by:** 无（03 的评审后续项与本票无关）

**Status:** done

## 现象与证据（2026-11-08 生产）

```
23:31:58  用户点「同步预演」
23:32:28  前端 axios timeout=30000 触发 → 弹「预演失败」，连接关闭
23:32:52  后端日志：钉钉通讯录预演：扫描部门 49 个 / 用户 368 人 / 耗时 54005 ms
                     （新增 322，补齐 0，疑似同名 46，跳过 0）
23:32:52  ERROR AsyncRequestNotUsableException: Broken pipe（写回时客户端已走）
```

- `frontend/src/api/http.ts:11` 全局 `timeout: 30000`，钉钉两个接口没有单独放宽。
- 数据库核对：预演后 `teacher` 仍 48 行、`dingtalk_user_id` 仍 0、`audit_log` 无 `DINGTALK_*` 行——**预演确实只读**。
- **危险点**：`confirm()` 先爬目录再写库，客户端 30 秒断开后后端仍会在第 54 秒完成写入，用户看到「失败」但数据已进库。

## 验收标准

- [x] 预演/确认两个请求单独使用 180 秒超时（不改全局 30 秒默认值）
- [x] 预演按钮在请求期间显示「正在拉取通讯录（约 1 分钟）」一类的进度文案
- [x] 目录加载并发化：默认 4 线程，可按 `paiban.integration.dingtalk.load-concurrency` 配置
- [x] 并发后**输出顺序与串行完全一致**（DFS 先序），预览分组不因线程调度而改变
- [x] 跨部门重复用户仍只出现一次，部门名按遍历顺序合并
- [x] 单个部门不可读仍只跳过该部门并计入 `failedDepartments`，不影响其余
- [x] IP 白名单等致命错误仍原样抛出（保持异常同一性）
- [x] 并发确实生效（用栅栏证明：串行实现会超时失败）
- [x] 线程池在任何路径下都被关闭（含异常）
- [x] 定向测试 + `verify.sh --quick` + `verify.sh --full` 全绿

## 不再做的

- 不引入「预演结果缓存供确认复用」——需要过期与一致性设计，本轮不做。
- 不动票 03 的 12 项（预演不显示匹配依据、部门 id 贯通、`/sync` 绕过预演等）。

## 风险

- 钉钉接口限流：4 并发约 8 次/秒，低于常见的 20 次/秒上限；若日志出现限流错误码，把 `load-concurrency` 降到 2。
- 兼容性：`DingTalkDirectoryLoader` 的对外契约（`load()` 返回值）不变，仅内部顺序保证方式改为「并发抓取 + 顺序装配」。
