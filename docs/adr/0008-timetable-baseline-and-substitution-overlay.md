# 课表数据采用"基线 + 调代叠加层"双表结构，默认展示合并视图

学期初发布的课表存储在 `timetable_entry` 表（基线），发布后**永不修改**。每次调代产生一条独立的 `substitution` 记录，包含生效日期、关联的基线条目、变更内容（换老师/换教室/换时间）、状态。查询课表时实时合并两者：默认视图显示"基线 + 截至当日的所有生效调代"，代课教师的格子带"（代）"标记。

## 为什么

- **可追溯**：原始发布版本完整保留，期末统计"某教师被代了几节""某教师代了几节""某班课表变过几次"都是简单 SQL，不需翻日志。
- **多视角**：同一套数据支持三种视图——最新执行（默认）、学期初原始、变更历史。
- **对比选项 A（直接改基线）**：A 让学期初原始课表失去追溯意义，被否。
- **对比选项 C（按周快照）**：C 每周物化一张新表，查询最快但存储与维护最重，中学规模下收益不足以抵消复杂度，被否。

## Consequences

- `timetable_entry` 表一旦 publish 即只读，任何修改必须通过 `substitution` 记录。
- 查询课表的 repository 层统一封装"基线 + 叠加"逻辑，业务代码不需要感知两张表的存在。
- UI 的"看原始 / 看变更历史"视图是廉价的副产品，一期即可交付。
- 调代审批通过后才产生 `substitution` 记录；审批中的申请单独存 `substitution_request` 表。
