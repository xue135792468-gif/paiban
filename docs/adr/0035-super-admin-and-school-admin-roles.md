# 预置角色改为超级管理员 / 教务管理员 / 老师

取代 [ADR-0006](0006-rbac-foundation.md) 的「预置 3 角色」名单。
RBAC 三表结构、权限点驱动授权、不写死角色名的结论继续有效，正文不改写。

## 背景

ADR-0006 的预置角色是「教务管理员 / 教师 / 班主任」，其中教务管理员全权。
学校只有一个人用的时候这没问题；一旦全校老师都要进来，同一个账号既管排课、又管账号、
又管钉钉集成，就没有任何职责边界，也没有「谁把谁降级了」的余地。
同时「班主任」这一身份在票 15 之后只剩两个按本班查看的权限点，产品上不再需要。

## 决定

预置角色固定为三种，账号页只能在这三种之间改身份：

| 编码 | 名称 | 权限 |
|---|---|---|
| `super_admin` | 超级管理员 | 除两个退休的按本班查看外，全部权限 |
| `admin` | 教务管理员 | 超级管理员减去「用户与角色管理」「集成配置」「账号审计查看」 |
| `teacher` | 老师 | 个人课表、本人授课任务、提交调代、本人调代记录、**只读查看全部课表** |

配套约束：

- `admin` 编码保留给教务管理员。授权仍沿用既有权限编码与判断入口（ADR-0006 原结论）：不新增按角色名
  鉴权的分支；只把原先「把只读查看当成管理」的具体判据按动作收紧（如课表发布通知的收件人判据
  从 `timetable:view` 改为 `timetable:edit`）。这类收紧逐条记在票 01 的核对清单里。
- 新增权限点 `audit:view:account`（账号审计查看），只给超级管理员；审计页面在票 02 落地。
- 升级迁移（V60）把旧 `admin` 角色持有者迁为 `super_admin`（保留旧授权，不只是 username=admin 的账号），
  旧 `head_teacher` 持有者迁为 `teacher`，随后删除班主任角色。业务数据一律不动。
- `timetable:view:class` / `substitution:view:class` 保留在权限目录里，但不分配给任何预置角色；
  按本班查调代的服务端分支保留，属后续清理。
- 启动种子只维护「角色 → 权限」对应关系，不再改动已有账号的角色：否则每次重启都会把
  被降级的教务管理员升回超级管理员。
- 最后一个**启用中**的超级管理员不能被降级、也不能被停用。降级与停用共用一个并发锚点：
  先锁 `super_admin` 角色行（稳定行，空集合时也有行可锁），再刷新目标账号，再用数据库标量
  count 判断「除目标之外是否还有启用中的超管」。用实体查询会读到持久化上下文里的旧
  `enabled = true`，让两个并发动作各自以为还有别人。

## 后果

- 老师拿到 `timetable:view` 之后，任何「把查看全部课表和其他权限组合起来当管理员判据」的地方都必须复核，
  核对清单写在票 01 的实现说明里。已发现的判据都不是单靠 `timetable:view`：
  调代工作台要「查看全部课表 + 提交 + 审批」三项，老师缺审批；
  课表发布通知的收件人判据从 `timetable:view` 改为 `timetable:edit`。
- 管理类通知的收件人（`adminUsers()`）同时包含 `admin` 与 `super_admin` 持有者，
  否则升级后「旧 admin 账号都变成超管」会让运维告警没有收件人。
- 少了一个可分配身份：班主任不再出现在任何列表里；按本班查看的入口随之下线。
- 二期开放自定义角色时，仍然只需要加界面与接口，权限判断点不变。
