# 整本工作簿导入在导入线程后台完成，计划与运行身份落库

日期：2026-10-26。实现票据：`.scratch/workbook-background/issues/01-background-progress.md`、`02-stop-abandon.md`、`03-retry-failed.md`。

## 为什么

ADR-0026 的整本导入仍然在一次 HTTP 请求里同步跑完：先用最多 6 轮只读工具规划结构，再按 40 行一批抄写取值，真实文件约 14 次模型调用、十余分钟。浏览器只能一直等；刷新就丢进度；任何一批失败会丢掉前面已读出的结果，也无法只重跑失败范围。

八期已经给单目标课表做了后台执行器、批次落盘、停止与重试。这批把同一组原则扩展到整本工作簿，但不复用「一批一个班」的数据结构：工作簿的批次是「一张工作表的一段数据范围」，身份必须带工作表、范围和计划版本。

## 决定

- 上传仍同步读取并 profile 文件（确定性、快），错文件照旧返回 400；规划与取值进入 `importExecutor`，上传立即返回 `PARSING`。
- 新增进度阶段 `PLANNING` / `EXTRACTING`。规划完成前 `total` 为 0，页面不显示伪造的批次数。
- `ai_import_log` 新增 `plan_json`、`plan_version`、`run_id`（V30）。计划落库后重试不再询问模型；每次重新规划递增版本，旧批次身份全部失效。
- 每个批次的身份为「工作表 + 1 基起始/结束数据行 + 计划版本」。批次随结果立即落盘，包含投影后的源行、列映射、结果与每一轮的原始回答；工具规划也每轮追加审计。
- `run_id` 标识当前有效运行。停止、放弃、重试都会替换或清空它；旧运行晚到的回答只追加到批次审计与 `ai_raw_response`，不能改状态、行或预览。
- 停止把未完成的批次标成失败（不是删除），所以有确认计划时「已停止」的会话是 `PARTIAL`（即使 0 个批次完成），未覆盖范围可见、可重试；停止发生在规划阶段、尚无确认计划时为 `FAILED`，页面提供显式「重新规划」。
- 重试只处理失败/未覆盖批次，成功批次不重复调用模型；合并始终从所有 `DONE` 批次重建整本槽位合并，跨表重复槽位仍只留一节。
- 任何批次未完成时前后端都拒绝入库；提交仍按 ADR-0026 的类别分事务。
- 整本工作簿的确认入库前先用一个短事务把会话认领为 `COMMITTING` 并 flush：乐观锁保证同一会话只有一个提交能进入类别写入，另一个得到 409。认领后失败放回 `PREVIEW`，进程重启把残留 `COMMITTING` 也放回 `PREVIEW`（票据 04）。单目标课表提交仍在一个事务里完成，不经过认领。
- 重启把残留 `PARSING` 会话收敛为 `PARTIAL`（有计划，未完成范围可重试）或 `FAILED`（无计划，需重新规划），不自动重放外部请求。
- 执行器拒绝任务时不留下「声称在解析、实际无人执行」的会话：首次上传 409 + `FAILED`，重试 409 + 回到 `PARTIAL`。

## Consequences

- 整本导入的 HTTP 语义从「等到预览」变为「立即返回会话 + 轮询」，与八期的大课表一致；单目标导入路径不变。
- 规划与取值共用一个单线程执行器，仍是串行；本批不引入按班/按表并发，避免供应商限流。
- 停止不能撤销已经发出的 HTTP 调用；它的结果是审计事件，不是有效结果。
- `batches_json` 的形态按工作簿重新定义；旧「每班一批」记录被识别为不可重试，只能重新规划，不会按索引误套到新计划上。
- `COMMITTING` 的启动恢复按单实例部署设计：重启会认为占用者已死。多实例部署需要额外的认领时间戳或心跳，避免误清另一实例正在进行的提交。
- 新增列全部可空或带默认值，部署时只需跑 V30。
